What is malbolge?

malbolge is a standard Malbolge implementation running inside the LOGIFUNGE shared IDE. Like brainfrick, it isn't a LOGIFUNGE dialect at all — it's a completely different, unrelated language that happens to fit the same engine interface the v1..v6 Befunge-style interpreters use, so it plugs into the same editor, step debugger, and output views with no changes to any of that shared code.

Malbolge, invented by Ben Olmstead in 1998, was deliberately designed to be almost impossible to program in. It's a ternary (base-3) virtual machine where every instruction rewrites itself the moment it runs, so a program's own source code is unrecognizable a few steps after it starts — the language is named after the eighth circle of Dante's hell for a reason. It took two years after Malbolge's release for the first working program (the classic "Hello, world!" below) to appear, and it wasn't written by a human: it was found by a beam-search program trying random instruction sequences.

The Machine

Three registers, all starting at 0: A (the accumulator, used by I/O and left holding the result of most operations), C (the code pointer — the address of the next instruction), and D (the data pointer, used by the data-manipulation instructions). Memory is 59,049 (310) words, addresses 0 to 59048, each word a 10-trit number. Code and data share this one address space, and there is no separate call stack or data stack.

The source is scanned left to right; whitespace is skipped entirely and doesn't occupy a memory word. Every other character must be printable ASCII 33-126 that decodes to one of the 8 valid instructions for its position — Malbolge's opcode is (address + character code) mod 94, so the same character means something different depending on where it sits in the source. A character that isn't a valid instruction at its address is a load-time error. Once the source is loaded, the rest of memory is filled by repeatedly applying the "crazy" operation (see below) to the previous two words.

i4C = [D] — jump: copies the value at [D] into the code pointer.

/23Read one character of input into A. A newline is code 10; end-of-file is code 59048.
*39[D] = A = rotate_right([D]) — rotates the value at [D] one trit to the right, and stores the result in both [D] and A.
j40D = [D] — moves the data pointer to the value it currently points at.
p62[D] = A = CRAZY(A, [D]) — the tritwise "crazy" operation, the only way to write an arbitrary value into memory (see below).
o68No-op.
v81Halt the program.

After each instruction runs — including updating C itself, for the jump instruction — the cell now at [C] is enciphered in place (a fixed mod-94 substitution) if it's still in the 33-126 range. This ordering is exactly why a jump's target gets enciphered instead of the jump instruction itself: C already points at the target by the time the encipher step runs. Finally both C and D are incremented (wrapping at 59049) and the cycle repeats. This self-modification is what makes Malbolge so hostile to write: a working instruction turns into something else the moment it's executed, so a naive loop breaks itself on its second pass. Practical Malbolge programs exploit specific weaknesses in the cipher's 2-cycles to work around this.

The Crazy Operation

A tritwise operation on A and [D]: each of the 10 trits of the result is looked up from the corresponding trit of [D] and A in a small fixed table. It's the only instruction that can write an arbitrary value into memory (* can only rotate what's already there), which is why almost every non-trivial Malbolge program leans on it, despite needing several supporting steps to use in practice.

Halting and Errors

A program ends when v executes, when C lands on a cell outside 33-126 (the reference interpreter is documented to hang here, which some published Malbolge programs rely on as a happy accident; this engine reports it as a runtime error instead, matching the language specification rather than that bug), or when the step limit is hit.

Input

Input works like a terminal, the same as for brainfrick. When the program reaches / with nothing left to read, it pauses and a blinking cursor appears at the end of the Output pane. Type a line and press Enter: the line (plus a newline, code 10) is echoed into the output and / reads it one character at a time. Press Ctrl+D to end input — after that every further / yields 59048, the value the specification defines for end-of-file.

Registers and Memory

The Stacks view for this engine shows two panels instead of the usual Data Stack + Memory pair: Registers, a small at-a-glance list of A, C, and D, each entry labeled (e.g. a: 123) so it's clear which value is which register, and Memory, a sparse view showing only the cells the program has actually read or written — not the full 59,049-word space, almost all of which is deterministic filler generated by the crazy operation and rarely worth inspecting. Malbolge has no separate data stack.

Using the IDE with malbolge

The IDE is the same one the v1-v6 and brainfrick engines use, with the same things tailored for a language with no 2D or pixel concept: the Pixel and Dual output views are hidden, since Malbolge has no pixel output — only Text and Stacks are shown. The editor highlights the source cell the code pointer currently occupies, for as long as it stays inside the region that was actually loaded from source; once C wanders into the crazy-filled memory beyond it (extremely common in real Malbolge programs), there's no source cell left to highlight. Step, Run, Speed, Max Steps, and syntax highlighting all work the same as on the other engines' pages.
